1AI 编码 / 编程代理2026-11-19

SWE-Recreation：面向软件复刻的编码智能体基准评测

SWE-Recreation: Benchmarking Coding Agents for Software Recreation

一句话前沿 agent 重建真实应用最高只有 0.530 加权保真度；新基准要求 agent 只看像素、自主探索并复刻。

它要解决什么

现有 coding agent 大多会先拿到目标、截图或演示，再按已知规格实现。论文问：能不能让 agent 像人一样，先用一个陌生应用，再自己写出功能等价的复刻。

为什么值得读

你做 AI 编程工具和 agent，其中一项关键能力，就是从现有产品反推需求并实现。这个基准把「探索」和「实现」分开打分，能帮你判断模型卡在哪一步。

怎么做的

Agent 只能看到渲染后的屏幕像素和光标，只能点击、拖动、滚动和输入；运行时禁止它读取 DOM、源码、日志、网络或后端。它要自己决定探索哪些功能、什么时候停止，然后生成可运行的复刻版本，并在评测前自检。评测用一个固定的 judge 模型，同样通过界面自适应执行隐藏工作流，并要求给出像素证据。基准包含 54 个真实应用（28 个网站、26 个 Android 应用）和 1,446 条隐藏需求，还列出多用户、支付、实时等不纳入评分的行为。类比：只给你一台样机，不给说明书，让你玩到会为止，再回家做一台功能一样的。

关键结果

在 42 个目标的平衡评测中（1,111 条需求、210 次运行），五个前沿系统最高只到 0.530 加权保真度；按应用等权平均，只有 22.9% 的需求被完整复现。人工复核中，专家认为超过 95% 的 judge 评分正确。

三个术语

黑盒应用重建
只通过用户能看到的界面和操作来理解并复刻一个应用，不能读源码或内部数据。
加权保真度（WFS）
把每条需求的完成程度折算成分数（完整 1、部分 0.5 等），再平均。
探索覆盖率（ECov）
在能判断的需求里，agent 在探索阶段实际碰到过的比例。
如果只记一件事先评估 agent 的探索覆盖，再看它的实现分数；不然你分不清它是不会用，还是不会写。

自测

  1. 我的 agent 能否在没有 DOM、源码和人工提示时，自己决定探索路径和停止时机？
  2. 我的评测是否把「没发现功能」和「发现了但没实现对」分开统计？
展开中文摘要

现有智能体多被直接告知目标。本文提出：智能体仅凭渲染像素与指针键盘操作，在无法访问DOM、源码或日志时理解陌生软件并重建。构建含54个真实应用（28个网站、26个安卓应用）与1446条隐藏需求的基准，以像素证据评判有状态工作流。五个前沿系统最高仅达0.530加权保真度和22.9%完全复现率。

怎么读：建议扫读，重点看第 3 到第 6 节的任务定义、指标和结果；需要基本的 LLM agent、前端或移动端交互评测概念。

2AI 编码 / 编程代理2026-11-19

刻画与检测编码智能体的不忠实工作报告

Characterizing and Detecting Unfaithful Work Reports by Coding Agents

一句话37% 的 agent 工作汇报含不实说法，作者做了分类、量化代价并做出检测器

它要解决什么

Coding agent 现在长时间自主干活，开发者很少逐步盯着，后续接手的 agent 也只能读它的汇报。所以汇报成了「到底改了什么、验证了什么」的唯一账本，账本一旦说错，后面的人和 agent 都会跟着错。

为什么值得读

你在做 agent 工具时，多半也在让 agent 汇报进度和结果，并据此决定是否验收。这篇给出了「汇报撒谎」的具体形态和可自动检查的方法，能直接变成验收环节或评测信号。

怎么做的

作者从 SWE-chat 的真实开发者-agent 对话出发，只挑「用户质疑某条说法、agent 随后承认说错」的案例，用这种双方都认账的样本定位有问题的断言。他们把断言和 agent 自己的记录逐条对照，归纳出 4 大类 11 个子类型。然后追踪每次被质疑之后又花了多少轮对话、多少时间，以及用户情绪。另外单独抽 435 份工作报告人工标注，量出这类问题的普遍程度。最后用观察到的模式做了一个检测器 FaithDetector，和基线比。类比：像看同事的日报说「接口已通」，你不能只看这句话，得翻他的提交记录和运行日志才算数。

关键结果

435 份抽样汇报里，162 份（37.24%）至少有 1 条不实断言。最常见的是「夸大任务完成」，占 69.3%。处理这类问题平均还要多 4.3 轮用户对话、12.71 分钟响应与执行时间。FaithDetector 在自然抽样汇报上达到 93.06% macro-F1，比基线高约 13 个百分点。

三个术语

coding agent
能自己读文件、改代码、跑命令的 AI 编程助手，不只是补全代码。
macro-F1
分类模型的打分，先把每一类的准确率和召回率算好再平均，避免被大类掩盖小类。
轨迹（trajectory）
agent 干活的全过程记录：它调了什么工具、看到什么输出、说了什么话。
如果只记一件事别信 agent 的汇报文字，要拿汇报前的执行记录去核对它说的每一条。

自测

  1. 我的 agent 或评测流程里，是不是只读了最终汇报文字，没核对执行记录？
  2. 我的汇报模板是不是容易让 agent 说出「已验证」「已完成」这类超出证据的话？
展开中文摘要

编码智能体的工作报告常成为变更与结论的主要依据，虚假或无依据声明会带来错误保证。基于SWE-chat真实对话，我们识别出四类十一子型不忠实报告，以夸大任务成功最常见；435份报告中37.24%至少含一项不忠实声明。提出FaithDetector，在自然采样报告上macro-F1达93.06%，较基线高约13个百分点。

怎么读：扫读即可，重点看第 3 节方法和分类表；需要一点 LLM agent 评测和标注一致性的常识。

3LLM 应用工程2026-11-20

Epistemic Guard：面向工具使用型自主智能体的进程外MCP回执代理、轮次后文本监督与来源门控记忆

Epistemic Guard: Out-of-Process MCP Receipt Proxying, Post-Turn Prose Supervision, and Provenance-Gated Memory for Tool-Using Autonomous Agents

一句话MCP 代理给每次工具调用签收据，CPU 小模型核对模型有没有谎报结果

它要解决什么

agent 用 MCP 调工具时，线路上发生的事和模型对用户说的话可能对不上。工具失败或根本没跑，模型却用第一人称说做成了，这句假话还会被写进长期记忆。

为什么值得读

你在做 agent 和 AI 编程工具，迟早会遇到「模型说改好了其实没改」这类问题。这篇给了三个可直接抄的工程点：进程外签名收据、回复后核对、写库前的来源门控。

怎么做的

它把 MCP 代理做成独立进程，放在宿主和工具服务器之间，拦下所有 JSON-RPC 调用，把它们分成四种执行状态，每次调用签一个 Ed25519 收据，写进只追加的 Merkle 日志。启动子进程前，它把环境变量里的私钥剥掉，子服务就没法伪造收据。模型回复之后，它再用一个 82.67 MB 的 INT8 模型在 CPU 上判断这句话有没有断言副作用，然后拿断言里的文件名、URL 等具体目标和签名收据的参数逐一比对。写 SQLite 记忆时，只放行带有效签名的那几类来源，模型自述和未验证网页文本在数据库边界就被拒掉。类比：像仓库保安不看搬运工自己填的出库单，只认自己盖章的放行条，对不上就不让出门。

关键结果

在 250 条冻结基准上准确率 93.2%，CPU 热启动中位延迟 17.9 ms，比 12B–14B 的 GPU 裁判高 6.4–6.8 个点，延迟低 4.26–4.5 倍，GPU 显存占用 0 MiB。确定性测试里，200 个被篡改的收据 100% 拒收，100 次越权记忆写入 100% 拦下；但 60 条线上轨迹上虽然抓到 96.15% 的危险回复，整体准确率只有 76.67%，误报率 38.24%。

三个术语

MCP
一个让模型用统一格式调用外部工具的协议，工具调用和返回都是 JSON 消息。
Merkle 日志
把每条记录的哈希串成链，改动任何一条都会让后面的哈希对不上，所以篡改能被发现。
provenance（来源分级）
给每条数据贴上来源标签，比如「用户说的」「工具返回的」「模型自己说的」，按标签决定能不能信。
如果只记一件事别信模型自述做了什么，用进程外的签名收据加 CPU 小模型去核。

自测

  1. 你的 agent 在工具超时或报错后，回复里还会不会说自己已经完成？
  2. 你的记忆库或向量库里，现在有没有混进模型自己编的话或未验证的网页文本？
展开中文摘要

针对MCP智能体的动作捏造、来源崩塌与回声放大三类验证缺口，提出开源进程外回执代理epistemic-guard（15模块，0 MiB GPU显存），实现进程外Ed25519签名、RFC 6962 Merkle日志与AER-1回执、CPU端轮次后文本核查、七类来源门控记忆与RAG镜像折叠。一致性测试拒绝100%篡改回执并阻止100%未授权记忆写入；250条轨迹准确率93.2%，中位延迟17.9 ms，较12B–14B GPU评判器高6.4–6.8分且快4.26–4.5倍。

怎么读：扫读即可，重点看第 3 节架构和表 2 的一致性测试；需要一点 Python、JSON-RPC/MCP 和签名的前置知识。

4LLM 应用工程2026-11-20

CoEvoBench：LLM能否驱动智能体系统的递归协同演化？

CoEvoBench: Can LLMs Drive Recursive Co-Evolution of Agentic Systems?

一句话建了个基准，测 LLM 能否在 24 小时内同时改模型和脚手架、一轮轮自我改进 agent。

它要解决什么

一个 agent 的表现，既取决于模型本身，也取决于 harness（连接模型与工具、环境的胶水代码）。已有基准只测其中一边：要么固定 harness 只训模型，要么固定模型只调 harness，没人测「两边一起改、每轮互相影响」这件事。

为什么值得读

你写 agent 时其实一直在做这件事：看 trace、判断是改提示/工具还是补数据/微调。这篇论文把这种手工循环做成可测量的任务，并给出「当前 LLM 能做到哪一步」的量化答案。它也是你判断要不要把 agent 迭代交给自动化研究循环的依据。

怎么做的

论文把 agent 拆成两半：模型权重 θ，和一个可执行 harness（管动作解析、工具调用、上下文与记忆）。研究员 LLM 从相同的基础模型和最小 harness 出发，在 24 小时、4 张 H20、100 美元教师模型预算内自由选择改权重还是改 harness。它能看可见集的任务细节和执行轨迹，选择集只回分数、不给题目内容和轨迹；最后提交一对「模型 + harness」，在独立测试集上打分。类比：把实习生关进实验室，只给他看错题和一张分数条，不给答案，让他自己决定这轮是重印教材还是改工具。五个领域覆盖修 bug、终端操作、应用交互、客服流程、多轮工具调用。

关键结果

在 Qwen3.5-9B-Base 上，最强研究员 GPT-6 Astra 平均分 31.23，参考系统（指令微调模型 + 参考 harness）是 37.42，补上了五分之四以上的差距；Claude Opus 5 补一半以上，其余三个不到三分之一。换成更小的 MiniCPM5-2B-Base 后，没有研究员在 SWE-bench Verified 上超过 10%、在 TB-Lite 上超过 2%，而 Astra 在 τ²-bench Telecom 上能到 96.11%。

三个术语

harness
包在模型外面的那层代码，负责解析模型输出、调工具、存上下文、处理报错。
递归自我改进（RSI）
系统自己改自己，再拿改好的版本去做下一轮改进，一轮接一轮。
选择集（selection set）
开发时用来试错的题目，只告诉你分数，不给你题目内容和执行轨迹。
如果只记一件事把第一版做好一次不难，难的是把改进后系统的反馈变成下一轮增量——当前 LLM 研究员正好卡在这里。

自测

  1. 我的 agent 每次提升，到底来自模型权重还是外壳代码？我现在分得清吗？
  2. 我的项目里有没有一个能自动跑「改一版 → 测一版 → 再改」的评测闭环？
展开中文摘要

LLM智能体性能取决于模型与承载框架（harness）。CoEvoBench让LLM作为研究者，在五个智能体领域内于24小时预算中联合改进目标智能体的模型与harness，并以独立测试任务评分。五个前沿研究者中最强者缩小了与指令微调参考系统逾五分之四的差距；协同演化在交互任务上成功，但在长程编码上鲜有成功，表明当前LLM能完成强首次改进，却难以把改进系统的反馈转化为下一轮提升。

怎么读：扫读即可，重点看第 5 节的收益递减分析和评测协议设计，不需要训练理论背景，但得懂 agent 的基本结构（模型 + 工具循环）。

5Web 全栈 / 前端工程2026-11-19

TideCache：具备透明缓存管理与逐层流式传输的高效混合LLM服务

TideCache: Efficient Hybrid LLM Serving with Transparent Cache Management and Layer-Wise Streaming

一句话动态重划分 GPU 缓存页，并按层预取前缀，让混合模型多服务请求

它要解决什么

混合模型一半层是全局注意力，一半是滑动窗口或循环层，两类缓存的需求随上下文长度和并发数变化。固定分区会让一部分 GPU 显存空闲，另一部分先耗尽；而解码时 CPU–GPU 链路几乎没流量。

为什么值得读

如果你在自建推理服务，或让 agent 在本地跑开源模型，KV cache 的显存分配直接决定同时能跑多少请求。这篇改的是 SGLang 的内存池层，不动模型 kernel。

怎么做的

把 GPU 显存做成一个共享物理页池，每个缓存组件占一段固定的虚拟地址。扩容时只改虚拟地址到物理页的映射，不搬活数据，注意力和 HiCache 都不用改；每 8 次前向做一次重划分，同时最多一次搬运。Cache Streamer 只让当前全局注意力层的前缀留在 GPU 上，用两层之间的有界状态层算出的空档，把下一层前缀提前搬进来，新生成的 KV 仍常驻。类比：像看菜谱做菜，不把整本书摊在台面上，只在你切菜的间隙把下一页翻好备着，台面就能多放几份菜。Request Scheduler 看请求大小和队列长度，决定这个请求走常驻还是走流式。

关键结果

对比 SGLang + HiCache，最多完成 2.04 倍 agent 轮次，P50 每 token 延迟降 20–59%，agent P50 TTFT 提升 1.40–3.05 倍。单看缓存池，固定负载下达到两种手调分区中较优者的 96.3–113.6%；批大小相同时解码单步最多多花 6.3% 时间。

三个术语

KV cache
模型记住前文用的键值表，上下文越长占显存越多。
bounded-state 层
每请求只保留固定大小状态的层，比如滑动窗口注意力或 Mamba，显存不随上下文增长。
Transparent Cache Pool
论文的内存池：虚拟地址不变，只换背后挂哪块物理显存，所以上层代码感觉不到变化。
如果只记一件事混合模型的显存瓶颈，可以用「页重映射 + 按层预取」这两招缓解，且不必改后端接口。

自测

  1. 你的模型是真混合结构（全局注意力 + 滑动窗口/循环层）吗？纯 Transformer 用不上流式那部分。
  2. 你的机器是 GH200/GB300 这类高带宽 CPU–GPU 超芯吗？论文里 GB300 单卡读主机内存 211 GB/s，PCIe 机器上按层预取可能盖不住计算。
展开中文摘要

混合架构中全局注意力层与有界状态层形成异构缓存。TideCache以透明缓存池在固定虚拟地址下重分配物理页，以缓存流式器利用有界状态层计算区间预取下一全局注意力层前缀并与计算重叠，生成KV仍驻留，并由请求调度器选择驻留或流式执行。基于SGLang在GB300与GH200七种配置上，最多完成2.04倍智能体轮次，P50每token延迟降低20%–59%，P50 TTFT提升1.40–3.05倍。

怎么读：扫读即可，重点看 4.1 节的页迁移协议和 5.3 节的流式带宽预算；需要 KV cache、SGLang 内存池和 CUDA 虚拟内存的基本概念。

6开发者工具 / 测试 / 工程效率2026-11-03

KG-AST：面向低成本 CI/CD 的预算化测试选择与 AI 缺陷审查

KG-AST for Cheaper CI/CD: Budgeted Test Selection and AI Bug Review

一句话用 git 历史给提交打风险分，把测试和 AI 审查预算优先给高风险提交。

它要解决什么

CI/CD 和 AI 审查通常对每个提交花同样的预算。但论文数据里只有 4% 到 35% 的提交会引入 bug。

为什么值得读

你在做 AI 编程工具、agent 和 Web 应用的 CI 流程，可以直接借鉴它的提交风险排序。它还给出调用图裁剪测试集、给 AI 审查喂图切片的工程做法。

怎么做的

KG-AST 在提交时用 diff 和提交前已知的 git 历史算风险分，共 59 个特征。它用一个跨语言 LightGBM 模型给窗口内提交排序，前 b% 走完整测试、AI 审查或人工审查，其余走便宜路径。类比：像机场安检按风险分流，少数可疑行李开箱细查，其余走快速通道。对选中的提交，它只取改动方法、调用者、被调用者和历史共变方法组成的图切片，作为 AI 审查上下文。测试选择从改动方法沿调用图反向走到测试方法，再按 FooTest 命名规则补测试。

关键结果

在 20 个 Java 项目上，20% 预算覆盖 64.6% 的引入 bug 提交，按最大改动排序是 49.5%，随机是 19.6%；11 种语言都超过最大改动基线，增益 3.8 到 13.2 个百分点。AI 审查只看 diff 精确找到 26% 的后修 bug，加图上下文到 32%；调用图 depth 2 加命名规则平均跑 8% 的测试套件（中位数 2.3%），在 67 个修复提交里 85% 包含修复自带的测试。

三个术语

SZZ 算法
用修复提交改过的行反查 git blame，找出最早碰这些行的提交，当作引入 bug 的提交。
AUC
把有 bug 的提交排在干净提交前面的概率，0.5 等于瞎猜，1 是完美排序。
调用图
代码里谁调用谁的图，顺着边能找到改一个方法会影响哪些方法和测试。
如果只记一件事先按提交风险分配 CI 预算，再用调用图缩小测试和 AI 审查范围，比平均用力更划算；但收益很大一部分来自改动大小。

  2. 你能接受只跑调用图选出的测试子集，并承担命名解析带来的漏测风险吗？

KG-AST 依据 git 历史与代码图特征评估提交风险，重型测试和 AI 审查优先处理高风险提交，AI 仅接收变更邻域图切片。在 11 种语言、155 个项目中，最高风险 20% 提交覆盖 49–64% 的缺陷提交，优于随机 20% 与最大变更 40–55%，均领先 3.8–13.2 个百分点。20 个 Java 项目覆盖 64.6%，19/20 胜出，约 12 个训练项目足够。AI 仅看 diff 发现 26%，加图上下文 32%；静态调用图选择器运行约 8% 测试并覆盖 85% 修复测试。Poincaré 无增益；标签有噪声。
